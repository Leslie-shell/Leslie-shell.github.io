Dubbo 服务治理

一、节点角色说明

  • Provider：暴露服务的服务提供方
  • Consumer：调用远程服务的服务消费方
  • Registry：服务注册与发现的注册中心
  • Monitor：统计服务调用次数和调用时间的监控中心
  • Container：服务运行容器

二、调用关系说明

  1. 服务容器负责启动、加载并运行服务提供者。
  2. 服务提供者启动时向注册中心注册所提供的服务。
  3. 服务消费者启动时向注册中心订阅所需服务。
  4. 注册中心返回服务提供者地址列表给消费者，如有变更，通过长连接推送更新数据。
  5. 消费者根据软负载均衡算法选择提供者调用，调用失败时重试其他提供者。
  6. 消费者和提供者在内存中累计调用次数和调用时间，每分钟发送一次统计数据到监控中心。

Guava 与 RateLimiter 限流

  • 背景

    • 应用或模块通常有访问速率上限。
    • 超过上限的请求不仅无法处理，还可能压垮系统。
    • 限流是保护系统的重要手段，Guava 的 RateLimiter 提供了简单易用的限流工具。

  • 常见限流算法

    1. 漏桶算法（Leaky Bucket）
      • 基本思想：请求进入系统时先放入缓存区，然后以固定速率流出进行处理。
      • 作用：平滑流量，防止瞬时高峰压垮系统。
    2. 令牌桶算法（Token Bucket）
      • 基本思想：桶中存放令牌，处理程序只有拿到令牌才能处理请求。
      • 如果没有令牌，请求要么被丢弃，要么等待令牌。
      • 限速方式：每单位时间产生固定数量令牌，例如每秒 1 个令牌。
      • 桶容量有限：未消耗的令牌可累积有限数量。

  • Guava RateLimiter API

  • 适用场景

    • 单机限流：直接使用 Guava RateLimiter。
    • 分布式限流：需要结合 Redis 或专业限流组件（如 Sentinel）实现集群级别的限流。

    • 水平拆分（分表）
  7. 应用拆分与服务化
    • 应用拆分
    • 服务化

    • 将内容分发到离用户最近的节点，加速访问

    • 放置静态资源（图片、JS、CSS 等）

大型网站核心架构要素

  1. 性能指标
    • PV、QPS、TPS、吞吐量、响应时间
  2. 吞吐量指标
    • TPS：每秒事务数
    • QPS：每秒查询数
    • HPS：每秒 HTTP 请求数
  3. Web 性能优化
    • 前端优化
      1. 浏览器缓存
      2. HTTP 请求合并
      3. CSS、JS、图片资源压缩合并
      4. CDN
      5. 页面静态化
      6. 减少 Cookie 传输
    • 服务端优化
      1. 接入层：反向代理、负载均衡
      2. 应用服务器集群
      3. 分布式缓存
      4. 数据库优化：索引、主从复制、读写分离、分库分表
      5. 分布式消息队列，异步操作
    • 单机并发优化
      • CPU 消耗：减少阻塞、同步转异步、队列、降低锁竞争
      • 文件 IO：异步读写、批量操作、限流、缓存、RAID
      • 内存消耗：减少不必要引用、对象池、缓存失效算法
      • 网络 IO：减少交互次数、减少传输量、异步非阻塞
  4. 抢购/超卖问题解决策略
    • 前端：页面静态化、CDN、禁止重复提交
    • 接入层：限制同 IP 访问频率、页面缓存
    • 服务层：Token 防刷、随机返回失败、数据库悲观锁
    • 数据层：主从复制、读写分离、分库分表
  5. 负载均衡
    • 算法：轮询、加权轮询、随机、最少连接、源地址散列
    • SSL 影响：需考虑负载均衡整合
  6. 安全性
    • XSS、SQL 注入、CSRF 等
    • 分类算法：贝叶斯
    • 黑名单：哈希表实现，但内存消耗大

链路追踪（Distributed Tracing）

  1. 定义

    • 将一次分布式请求还原成调用链路
    • 展示各服务节点耗时、请求状态及到达的具体机器

  2. 主要功能

    • 故障快速定位：结合调用链和日志快速定位错误
    • 链路性能可视化：展示阶段耗时和服务依赖关系
    • 链路分析：分析用户行为路径和业务统计

  3. 常用系统

    • 国际：Zipkin、Jaeger、Pinpoint、SkyWalking
    • 国内：阿里鹰眼、美团 Mtrace、滴滴 Trace、新浪 Watchman、京东 Hydra

  4. 开源组件链接

    • Zipkin
    • Jaeger
    • Pinpoint
    • SkyWalking

  5. Zipkin 核心组件

    • Collector：采集链路数据，验证、存储、索引

    • Storage：保存链路信息，支持 Cassandra、Elasticsearch、MySQL

    • Query Service：提供 JSON API 查询链路数据

    • Web UI：可视化展示调用链信息，辅助运维

分布式链路追踪（Zipkin）

  • 概述
    • 在服务运行过程中会产生大量链路信息，产生数据的地方称为 Reporter。
    • Reporter 将链路信息通过 HTTP、RPC、Kafka 等方式发送到 Zipkin 的采集器（Collector）。
    • Zipkin 处理后将链路信息保存到存储器（Storage）中，运维人员可通过 Web UI 查询调用链信息。
  • Zipkin 核心组件
    1. Collector
      • 采集线程获取链路追踪数据后，Zipkin 对其进行验证、存储和索引，并调用存储接口保存数据，以便查询。
    2. Storage
      • 最初为 Cassandra 构建，支持可伸缩存储和灵活模式。
      • 也支持 ElasticSearch、MySQL，后续可扩展第三方存储。
    3. Query Service
      • 存储和索引后的数据可以通过 Query Service 查询，提供 JSON API，方便运维快速定位问题。
    4. Web UI
      • 提供查询、搜索界面，运维人员可直观查看调用链信息，快速识别线上问题。
  • 总结
    • 分布式链路追踪就是将每一次分布式请求还原成调用链路。
    • 核心概念：Trace、Span、Annotation、带内和带外数据、采样、存储。
    • 开源组件多基于 Google Dapper 论文演变而来。
    • Zipkin 核心组件：Collector、Storage、Query Service、Web UI。

多线程基础概念

1. 多线程核心概念

  • 同步 (Synchronous) 与 异步 (Asynchronous)
  • 并发 (Concurrency) 与 并行 (Parallelism)
  • 临界区 (Critical Section)
    • 临界区表示共享资源，每次只能有一个线程访问，其他线程必须等待。
  • 阻塞 (Blocking) 与 非阻塞 (Non-Blocking)
  • 死锁 (Deadlock)、饥饿 (Starvation) 与 活锁 (Livelock)
    • 饥饿：某些线程无法获得资源，一直无法执行。
    • 活锁：线程主动释放资源给其他线程，但资源不断在线程间跳动，导致没有线程能完成任务。

2. 并发级别

  • 并发级别受临界区控制策略影响，可分为：
    • 阻塞 (Blocking)
    • 无饥饿 (No Starvation)
    • 无障碍 (Barrier-Free)
    • 无锁 (Lock-Free)
    • 无等待 (Wait-Free)

3. 并行的两条定律

  • Amdahl 定律 (阿姆达尔定律)

    • 定义并行化后的加速比理论上限。
    • 加速比 = 优化前耗时 / 优化后耗时

  • Gustafson 定律

    • 如果可并行化的代码比例足够大，加速比随 CPU 数量线性增长。

Consul 优势与应用场景

  1. Consul 优势
    • 服务注册与发现
      • 提供 DNS 或 RESTful 接口的方式进行服务注册和发现。
      • 服务可根据实际情况选择使用方式。
    • 健康检查
      • Client 可提供任意数量的健康检查。
      • 健康检查既可与服务关联，也可与本地节点关联。
    • 多数据中心支持
      • 支持多数据中心部署，保证高可用性与扩展能力。
    • Gossip Protocol
      • 实现多数据中心无需配置服务器地址，服务发现自动完成。
      • 健康检查故障处理分布式完成，不依赖单点服务器。
  2. Consul 使用场景
    • 服务注册与发现
      • Consul 作为注册中心，服务注册后可通过 DNS 或 HTTP 接口查询。
      • 支持健康检查（Health Check）功能。
    • 服务隔离
      • 可按服务设置访问策略。
      • 支持传统平台和新兴平台，TLS 证书分发及 Service-to-Service 加密。
    • 服务配置
      • 提供 Key-Value 数据存储功能。
      • 配置变更可快速通知服务，实现配置共享与动态更新。

核心理念：Consul 提供高可用、可扩展的服务注册与发现、健康检查、服务隔离及配置管理能力，适用于分布式系统的服务治理。

Java 虚拟线程（Virtual Threads

1. 概述

虚拟线程（Virtual Thread）是 Java Project Loom 提供的一种轻量级线程。
它由 JVM 调度，而不是由操作系统调度，因此可以创建海量线程，适合 I/O 密集型任务。

传统线程 = OS 线程
虚拟线程 = JVM 管理的轻量线程（类似 goroutine / coroutine）

2. 虚拟线程解决了什么问题

2.1 阻塞 I/O 导致资源浪费

传统线程在执行 I/O（数据库、网络、文件）时会阻塞 OS 线程，导致：

  • 线程占着内核资源却在等待
  • 大量线程导致上下文切换开销大
  • 系统可承载并发有限（几千级）

MySQL 函数（Function）

1.1 定义

函数就是一个可以返回单个值的 SQL 代码块。
它可以接收参数，做计算或处理，然后返回一个结果。

  • READS SQL DATA：函数内是否读取数据

什么是窗口函数？

一句话：

窗口函数 = 在不分组的情况下，对某一范围（窗口）内的多行数据做计算，并把结果“附加”到每一行上。

它不会把多行合并为一行（不像 GROUP BY）。
它只是“看一下周围的行”，然后计算。
