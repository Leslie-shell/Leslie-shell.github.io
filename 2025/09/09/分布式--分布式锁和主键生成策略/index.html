分布式锁和主键生成策略

分布式系统核心

1. CAP 原则

  • CAP 原则告诉我们：在分布式系统中，一致性 (Consistency)、可用性 (Availability)、分区容错性 (Partition tolerance) 三者不可兼得。
  • 参考文章：
    • SegmentFault: CAP 原则
    • 博客园：CAP 原则详解

2. 分布式锁要求

  • 在分布式部署的应用中，同一个方法在同一时间只能被一台机器上的一个线程执行。
  • 锁应具备：
    1. 可重入：避免死锁
    2. 阻塞锁（根据业务需求决定）
    3. 高可用的获取锁与释放锁
    4. 高性能

3. 分布式锁实现方式

3.1 数据库实现分布式锁

3.1.1 基于数据库表

  • 方法：
    • 加锁时在表中插入一条记录
    • 解锁时删除该记录
  • 缺点：
    • 数据库单点问题 → 可做双库同步和切换
    • 无锁超时机制 → 可做定时任务清理超时记录
    • 非阻塞 → 可使用循环等待 insert 成功
    • 非重入 → 在表中记录机器和线程信息，允许同线程重复获取锁

3.1.2 基于数据库排他锁

  • 使用 SELECT ... FOR UPDATE 给行加锁
  • 注意：
    • InnoDB 行级锁需通过索引查询
    • 索引必须唯一，避免冲突
    • 阻塞锁：查询失败时线程阻塞，直到成功
    • 服务宕机 → 数据库会自动释放锁

参考文章：CSDN 详解

3.2 基于 Redis 缓存实现分布式锁

  • 使用 SETNX（set if not exist）命令：
    • 成功返回 1 → 获得锁
    • 失败返回 0 → 未获得锁
  • 使用 DEL 命令释放锁
  • 可设置锁 超时时间 → 避免服务宕机导致锁无法释放

参考文章：SegmentFault Redis 分布式锁

3.3 基于 ZooKeeper 实现分布式锁

  • 思路：
    • 客户端加锁时，在 ZooKeeper 上生成 瞬时有序节点
    • 判断锁是否获取：节点序号最小的客户端获得锁
    • 释放锁时删除节点
  • 优势：
    • 服务宕机自动释放锁
    • 避免死锁问题

4. 分布式数据库主键生成策略

  • 常用方式：
    • 雪花算法（Snowflake）
    • Meituan Leaf 分布式 ID 生成
  • 参考：
    • 简书：分布式主键生成
    • 美团技术：MT_Leaf

5. 反向代理（Reverse Proxy）

  • 代理服务器接收客户端请求 → 转发给内部服务器 → 返回结果给客户端
  • 客户端只看到代理 IP，不知道内部服务器存在

6. 负载均衡（Load Balancing）

  • 将请求或任务分配到多个服务器、CPU 或资源上，提高吞吐量与可靠性
  • 目标：
    • 最大化资源利用
    • 最小化响应时间
    • 避免单点过载
  • 实现方式：
    • 软件或硬件负载均衡
    • 通过冗余提高可靠性
