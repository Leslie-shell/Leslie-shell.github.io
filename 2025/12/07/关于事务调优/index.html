Spring 事务调优总结

Spring 中的事务由 代理 + Connection + 数据库锁 三者共同协作完成。
事务调优，就是让事务执行更快、更短、更稳，并减少锁竞争。

为什么需要事务调优？

默认情况下事务可能会：

  • 启动太早、结束太晚（锁占用时间太长）
  • 事务方法嵌套造成多次创建、失效
  • 使用默认隔离级别导致锁冲突严重
  • 连接池等待过长导致“卡死感”
  • 事务回滚太重，放大性能问题

事务慢 = 锁持有时间长 = 数据库吞吐量下降 = 性能雪崩

常见事务性能问题（踩坑总结）

✔ 2.1 事务范围过大（最常见）

这会导致：

  • Connection 长时间占用
  • 行锁/表锁长时间占用
  • 整体吞吐量下降

✔ 2.2 在事务中执行外部请求（致命问题）

HTTP、Redis、MQ、上传文件都不能放在事务里。

✔ 2.3 使用默认隔离级别造成锁冲突

MySQL 默认：

  • REPEATABLE_READ
  • 可能导致 gap lock、next-key lock 过重

✔ 2.4 事务失效导致子逻辑没有事务保护

常见原因：

  • 同类内部方法调用
  • private/final 方法
  • 未被代理

✔ 2.5 长事务导致死锁

事务越长，越容易造成死锁。

✔ 2.6 锁粒度过大，没建索引导致全表锁

事务调优策略（核心）

🟦 3.1 缩小事务范围（最关键的优化）

确保事务只包含“必须要有事务语义的代码”：

✔ 只把 更新数据库的代码 放进事务
✘ 不要把 RPC/IO/复杂计算 放入事务
✔ 复杂逻辑拆分成多个事务方法

3.2 减少事务中的 SQL 数量

事务里的 SQL 越多，锁时间越长。

  • 合并 SQL（使用 batch/批量）
  • 避免循环中执行 SQL
  • 使用 JOIN 替代多次查询

3.3 调整事务隔离级别（减少锁）

隔离级别 性能 脏读 幻读 使用场景
READ_UNCOMMITTED ★★★★★ ✓ ✓ 极少数高吞吐场景
READ_COMMITTED ★★★★ ✗ ✓ 大部分互联网系统最推荐
REPEATABLE_READ（默认） ★★★ ✗ ✗ 需要一致性，而非高并发
SERIALIZABLE ★ ✗ ✗ 强一致性需求

高并发系统建议：READ_COMMITTED
