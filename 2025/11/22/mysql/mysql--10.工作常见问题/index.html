1.2 MySQL 逻辑架构

  1. 客户端

    • 连接器

    • 解析器（Parser）
    • 优化器（Optimizer）
  3. 存储引擎（InnoDB 等）

1.3 优化和执行

  • 查询解析和优化
    • MySQL 会解析 SQL 查询，生成内部解析树。
    • 优化器会重写查询、选择表的读取顺序、选择合适索引。
    • 用户可以通过关键字（如 STRAIGHT_JOIN、FORCE INDEX）提示优化器，影响决策。
  • 查询缓存（已废弃）
    • 5.6 默认关闭（query_cache_type=0），8.0 已删除。
    • 查询缓存问题：
      • 受到单个全局互斥锁 query_cache_lock 保护，高并发下成为瓶颈。
      • 写操作（INSERT/UPDATE/DELETE/DDL）会使相关缓存失效，持有全局锁阻塞其他操作。
    • 高并发场景下，缓存反而会导致性能下降。

2. MySQL 行存储

2.1 数据库文件存放位置

  • 默认路径：/var/lib/mysql/
  • 每个数据库会生成一个目录，存放该数据库的表结构和数据：
    1. db.opt：存储数据库默认字符集和校验规则
    2. t_order.frm：保存表结构（元数据）
    3. t_order.ibd：保存表数据（InnoDB 表空间）

2.2 表空间结构

  • InnoDB 表空间逻辑结构：
    • 段（Segment） → 区（Extent） → 页（Page） → 行（Row）

2.3 NULL 值存储

  • Compact 行格式中使用「NULL 值列表」标记 NULL 列。
  • NULL 值不占行数据实际空间，仅占用 1 字节。
  • 所有字段为 NOT NULL 时，省掉 1 字节空间。

2.4 VARCHAR 实际占用

  • 通过「变长字段长度列表」记录实际占用大小。
  • 最大值：65535，需减去其他字段长度、变长字段长度列表及 NULL 列表空间。

5. MySQL 索引

5.1 B+ 树索引原因

  • 支持范围查询和排序
  • 叶子节点形成链表，方便顺序访问
  • 层级较低、IO 少，适合磁盘存储

5.2 COUNT 性能分析

方式 说明 性能
count(*) 统计所有行，无论 NULL 高
count(1) 类似 count(*)，不判断列 高
count(主键字段) 只统计主键列 较高
count(字段) 统计字段不为 NULL 的记录 低（全表扫描）
  • 执行过程：
    • count(*) 会转化参数为 0，InnoDB 处理与 count(1) 相同，无性能差异。
  • 优化建议：
    • 对大表频繁统计，可：
      1. 使用 EXPLAIN 返回近似行数
      2. 维护计数表
    • 尽量使用二级索引统计，提高 IO 性能。

6. MySQL 优化实践

6.1 优化原因

  • 数据库访问速度决定系统吞吐量
  • 数据量增大，磁盘读写瓶颈明显
  • SQL 优化收效有限，需要多层次优化

6.2 优化策略

  1. 数据库设计
    • 表结构、字段类型、存储引擎选择
  2. 索引利用
  3. 横向扩展
    • MySQL 集群
    • 读写分离
    • 负载均衡
  4. SQL 优化
    • 精简字段
    • 避免全表扫描

6.3 字段设计建议

类型 建议 说明
整型表示状态 用整型代替字符串 如 IP、状态码
IP INET_ATON/INET_NTOA 查询性能高、索引小
枚举/集合 使用关联表代替 MySQL 枚举 维护成本低
小数/金额 使用 DECIMAL 定点数 精度高
字符串 定长 CHAR / 非定长 VARCHAR / TEXT 注意最大长度、长度存储消耗

6.4 IP 存整型的优势

  • 查询性能：
    • 等值查询快 10–100 倍
    • 范围查询快 1000 倍以上
  • 索引效率：
    • 索引体积小 3–4 倍
    • B+ 树高度低，减少磁盘 I/O
  • 数据一致性：
    • 杜绝前导零、空格、大小写问题
    • 外键关联查询快 5–10 倍
  • 可扩展性：
    • 支持 IPv6，使用 VARBINARY(16) 扩展
  • 实测数据（基于 MySQL 8.0 + InnoDB）
场景 VARCHAR (字符串) INT UNSIGNED (整型) 性能差距
等值查询 (1000万行) 120 ms 0.5 ms 快 240 倍
IP 段查询 (BETWEEN) 4200 ms 2 ms 快 2100 倍
索引大小 220 MB 70 MB 缩小 70%
  • 结论：
    • 核心价值：查询性能提升、索引效率提升、数据一致性强
    • 实施成本低：写入时 INET_ATON()，查询时 INET_NTOA()，业务无感知
